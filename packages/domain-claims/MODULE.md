## Responsibility

Owns the claim case: its lifecycle state and the guarded transition between states, assignment to a staff owner, the staff and admin read scopes, the support handoff, and the claim pack. The event table is the case history.

## Public API

The staff and admin actions call `changeClaimStatus` from `./claims/change-status` and `changeClaimAssignment` from `./staff-claims/assign`. Both commands take the actor from the tenant authority principal. `./claims/transition-guard` exposes the status graph and guard. Submission, creation and draft updates use `./claims/submit`, `./claims/create` and `./claims/draft`.

`./claims/service-level` calculates deadlines in Europe/Skopje. `./claims/service-level-report` counts claim requests and support handoffs. Set the server environment variable `SERVICE_LEVEL_REPORTING_START` to an ISO date in UTC or an ISO instant with an offset. The report returns `reporting_start_unset` when that setting is missing or unparseable.

`./staff-claims/scope` exposes `buildStaffClaimReadScope` for staff-recipient eligibility and `canStaffReadClaim` for applying it in a caller-owned transaction.

## Invariants

- There is **no `status` column**: the status is the pair `case_lifecycle_state` + `recovery_lifecycle_state` with a `lifecycle_version` counter (`packages/database/src/schema/claim-core.ts:36-48`; mapping at `src/claims/lifecycle-state.ts:18-55`). Nine statuses (`A/modules/case-handoff.md:47`).
- Only 27 directed transitions are allowed, plus a same-status call — enforced in code by `ALLOWED_CLAIM_STATUS_TRANSITIONS` (`src/claims/transition-guard.ts:50-60,66-69`, MEASURED in `A/modules/case-handoff.md:51`). Database CHECKs pin the status pairs (`packages/database/src/schema/claim-core.ts:84-101`).
- The staff and admin actions use the shared status command. It locks the scoped claim, applies the decline and recovery prerequisites and checks the lifecycle guard before writing. The lifecycle version also guards the write. Recovery transitions lock the agreement and membership inputs and use one effective time for coverage and usage.
- Claim numbers are unique within a tenant and allocated atomically — database: unique `(tenant_id, claim_number)` and a counter PK `(tenant_id, year)` (`schema/claim-core.ts:83`; `packages/database/src/claim-number.ts:128-138`).
- A claim is assigned only to staff who can see it — **NOT ENFORCED** (CASE-01, S2): a claim can be assigned to staff of another branch, who then cannot open it, and nobody is alerted (`src/staff-claims/assign.ts` and `src/staff-claims/scope.ts`). Root cause: **five different staff-scope predicates** (CASE-05, `scope.ts:24-36`, `access-policy.ts:46-63`, `upload/server/access.ts:47-51`).
- A claim always has a branch — **NOT ENFORCED**: a claim without one is invisible to branch-bound staff queues (CASE-08, `submit-assignment.ts:121`; `staff-claims-list-filters.ts:51-53`).
- A message is refused on a closed claim — **NOT ENFORCED** (CASE-06, `actions/messages/send.ts:39-55`: the send never reads the claim's status). A public staff reply notifies the owner and answers open requests. A qualifying owner message creates a response request and notifies scoped staff or the tenant administrator.
- The case history is complete and append-only — **NOT ENFORCED**: audit tables are mutable in the database and three paths write the audit row **after** commit and swallow the failure (DATA-06; CASE-12, `lib/audit.core.ts:46-81`).
- Claim amounts are integers in minor units with a currency — **NOT ENFORCED**: `amount decimal(10,2)`, nullable `currency text DEFAULT 'EUR'`, no CHECK (`schema/claim-core.ts:53-54`).
- A claim document belongs to its claim's tenant — application only for plain evidence; the database enforces it with composite FKs for request-linked evidence (`schema/claim-support-tables.ts:19-25,40`; `drizzle/0094_request_linked_evidence.sql:20-21`).

## Tenant boundary

`./claims/send-message` composes the message write, response requests and notifications in one tenant transaction. Staff routing and the send-time staff eligibility check use the same staff claim read scope. `./claims/notification-delivery-runner` drives the queue through the communications worker operations.

Reads and writes run inside `withTenantAuthority`; the staff read scope adds branch and ownership predicates on top (`src/staff-claims/scope.ts:24-36`). Document access on this journey is tenant-bound and role-bound (`A/modules/case-handoff.md:204`: full-tenant roles, owner, uploader, staff only when `staffId` = self, agent scope, case grant, never staff on a draft). R1 found **no cross-tenant or cross-member reachability** in the files it read, with the cross-tenant grant fallback and the agent document scope **not opened** (`A/modules/case-handoff.md:206`).

## Decided for this module (owner, 2026-11-17; decisions, not verified properties of today's code)

- A status that the member can see notifies the member, from every entry point (answer 16; CASE-03 is a defect, WP-11).
- Staff get no access to a member's draft, protected files included; a branch manager sees no document, message or note content, only counts; staff have no free private chat: every internal message is tied to a case or a request and is audited (answer 27 b, c, d).
- **The correspondence register (WP-12, answer 31).** A new table `claim_correspondence`, owned here; `claim_threads` is not reused (it has no caller and models a conversation). The assigned staff member and the administrators record (the assigned-staff check is that of `src/claims/information-requests.ts:55-64`); every other role that can open the case reads only, and a branch manager sees the number of records and their dates, not their content (answer 27 c applied to the register; the pilot has no branch manager). Stored about the outside party: the organisation, its reference, the channel; a named contact person may be stored, is kept for the case's retention period and is deleted with the case. The name stands only on the register's row, which goes with its claim; no log line, audit payload or other table copies it; the deletion itself waits for WP-13. **The legal basis** (this contract's word for the four values, to keep them apart from the authorization basis of an action, R-05) is one of: an accepted, versioned recovery agreement; an active, case-specific, jurisdiction-appropriate power of attorney or equivalent authority; a signed assignment; a versioned purpose-specific consent or lawful-basis evidence — each with its scope and its expiry; a revoked or expired basis refuses a new outbound record at once and keeps the history. **The value classifies the evidence; it does not by itself authorize an action** (closing pass, review comment R3-C04): an outward action can need several bases together — the baseline asks for the agreement and the authority before a contact on the member's behalf (IDA-SVC-014) — and which bases, in which scope and jurisdiction, each action of the pilot needs is an acceptance criterion of WP-12 (`docs/engineering/DIRECTION.md`). Professional recovery and VONESA stay outside the pilot. **That rule needs something to read** (found by the drill of R3): today only the first value has a table (`claim_escalation_agreements`, `packages/database/src/schema/claim-commercial.ts:30-89`: a terms version, the signed and the accepted time, no expiry and no revocation), and the three others have none. WP-12 therefore adds a second table, owned here: the authorities of a case — the kind, its reference, its version, its scope, the time it was given, its expiry, and the time and the actor of a revocation. An outbound record cites one authority of the same claim through a tenant-bound key and is refused when that authority is revoked or expired. **How the recording and the revocation are kept from passing each other is not decided here** (closing pass, review comment R3-C03; the earlier text promised it from a condition inside the insert, which does not give it: the insert can read the authority as valid while a revocation commits). WP-12 defines one synchronization that both commands use, names the moment at which the authorization is decided, checks scope and expiry again at that moment, and shows both orders with a test on two connections (`docs/engineering/DIRECTION.md`, WP-12; R-17). A revocation sets a time and deletes nothing. The follow-up time is an instant with an offset, like the due time of an information request (`src/claims/information-requests.ts:32`); it has passed when it is earlier than the moment of the read, computed at read time (`src/staff-claims/assigned-claim-attention.ts:44-50`), and it shows in the staff list; there is no reminder and no job. Shared documents are cited by share-pack id: the pack is built before the command's transaction, and the command checks through the documents package's query that the pack belongs to this case. The columns, the commands and the files are planned in `docs/engineering/FEATURE-RECIPES.md` (recipe 2); the implementer writes the final columns into this contract with the table (R-19).
